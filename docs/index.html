01 / 阅读地图

先知道我们在解决什么问题

一份已经训练好的 AI 模型，通常还需要经过接口适配、计算图导出、数值验证和目标芯片编译，才能成为开发板上可用的推理组件。

这篇文章讲的是一个具体项目：将本地 Qwen3 0.6B、Gemma3 1B、TinyLlama 1.1B 和 Qwen3.5A 2B 检查点，适配为面向 Ascend310B4 的 OM 模型。其中，Qwen3.5 保留文字与单张图片输入，制作了 640×640 / context 1024 和 768×768 / context 2048 两组规格。

你不需要先学会 Python，也不需要熟悉神经网络公式。每出现一个新术语，正文会先解释它的用途，再给出它在项目里的具体含义。折叠框放置更深入的细节，第一次阅读可以跳过。

第一次接触模型从文件与 token 开始，按顺序阅读。已经用过聊天模型先看转换流程，再回查缓存概念。最关心图片输入从视觉链路开始，结合后面的预算实验。
本文有三种不同性质的信息

通用原理解释模型为什么这样工作；本项目实现描述实际导出器做了什么；验证结果只陈述构建记录已经证明的内容。比如“ATC 编译成功”证明工具链生成了 OM，但它本身并不包含开发板推理速度或真实照片识别质量的结论。

你可以先记住四个动词：加载已有权重，表达推理运算，核对转换前后的结果，再编译到目标芯片。整篇文章都会围绕这条主线展开。

02 / 模型与文件

一个模型，不只是一个权重文件

先理解“参数”与“训练权重”

神经网络内部有大量矩阵和向量。它们控制怎样把输入变成中间特征，又怎样把中间特征变成下一步输出。这些需要学习的数值叫参数。训练完成后，保存下来的参数通常叫权重。

“1B”中的 B 是 billion，也就是十亿。1B 模型大致有十亿个参数，2B 大致有二十亿个参数。这个名称是规模标签，不表示每个模型恰好有一个整数数量的参数，也不能单独决定它在某项任务上的效果。

可以这样类比

把模型想成一座已经调好设备的工厂：权重像设备的设置值，网络结构像生产线的连接方式，tokenizer 和图像预处理像原料进入工厂前的分拣规则。只有设置值，没有生产线和原料规则，工厂仍然无法正确开工。

safetensors、config、tokenizer 分别负责什么

常见文件主要内容缺少它会怎样
*.safetensors矩阵、向量等权重张量，也可能分成多个分片。没有模型学习到的参数。
config.json层数、隐藏维度、注意力头、位置编码、架构类型等。无法可靠地按正确结构组装权重。
权重分片索引记录每个张量保存在哪个分片里。大模型可能无法完整加载。
tokenizer.json 等文字与 token ID 之间的映射和切分规则。文字会被错误编码，输出 ID 也无法正确还原。
聊天模板用户、助手、系统等角色如何排列，哪里开始生成。即使模型计算正常，也可能因为输入格式不对而表现异常。
processor / 图像预处理配置图片怎样缩放、归一化、组织 patch 和图像占位符。视觉输入的数值与顺序可能不符合模型要求。

因此，这个项目使用的是完整本地模型目录。导出时要保留权重和对应的结构、分词、模板、预处理信息之间的关系。文件后缀相同，并不说明两个模型能够使用同一个导出器。

BF16、FP16、FP32：数字怎样存

计算机用有限的二进制位保存实数。FP32 使用 32 位，通常每个数占 4 字节；FP16 和 BF16 都使用 16 位，通常每个数占 2 字节。FP16 与 BF16 把位数分配给指数和尾数的方式不同：BF16 覆盖的数值范围更大，FP16 在它能表示的许多数值区间内有更细的刻度。二者并不是同一种编码。

项目中的 Qwen3、Gemma3 和 TinyLlama 原始张量存储为 BF16，导出主要使用 FP16。Qwen3.5A 的原始张量为 FP16，成功的图文图又为部分计算选择了 FP32。每一次精度安排都要通过数值验证，不能只看“都是 16 位”就认为结果必然一样。

最基本的权重存储估算 ≈ 参数个数 × 每个参数的字节数

例如十亿个 FP16 数，原始数值本身约占 20 亿字节，即约 1.86 GiB。这是参数数据的估算，不是模型运行时的完整内存占用，也不是编译后 OM 大小的精确预测。

操作主要改变什么本项目中的位置
训练 / 微调通过数据与优化过程更新权重。本文使用已有训练权重，不执行这些步骤。
浮点精度转换改变数值的存储或计算格式。BF16、FP16、FP32 的安排与验证。
低位整数 / 权重量化用 INT8、INT4 等表示参数，通常还要选择量化方案。本文这些交付没有实施 INT8 / INT4 量化。
导出把框架推理过程表达为另一种计算图。PyTorch → ONNX。
编译针对目标硬件生成可运行模型。ONNX → Ascend OM。
03 / 推理的基本过程

模型怎样一个 token、一个 token 地回答

token 是模型处理文字的单位

token 可以对应一个字、一段词、标点，或者其他切分片段。一个 token 不固定等于一个汉字，也不固定等于一个英文单词。不同 tokenizer 对同一句话的切分可能不同，因此同样的 context 数值，不意味着能装下完全相同数量的文字。

tokenizer 把文本变成整数 ID；embedding 层再把每个 ID 映射成一组连续数值，称为嵌入向量。网络处理这些向量，最后给词表中的候选 token 打分。这些还没有经过概率归一化的分数叫 logits。

根据 logits，可以选分数最高的 token，这叫贪心选择；也可以按一定规则随机采样。选出一个 token 后，再把它送回模型，生成下一个。最后 tokenizer 把这些 ID 还原成可读文字。

文字 → token ID → embedding 向量 → 多层网络 → logits
                                               ↓
                                     选择下一个 token
                                               ↓
                                     送回模型，继续生成

Prefill 与 Decode 是两个阶段

Prefill（预填充）是先读完用户输入和聊天模板，把相关状态建立起来。Decode（逐步生成）是在已有状态上，每次处理新 token 并预测下一个。

许多通用推理框架会一次或分块处理提示词，再逐 token 生成。本项目的固定接口主要采用单 token 步进：提示词也按顺序一步一步送入。这样的接口便于导出和核对，但首个回答出现前，需要完成全部提示词步骤，不能把其他框架的速度直接套过来。

最容易写错的交接点

处理最后一个提示词 token 后，模型输出的 logits 就用于选择第一个回答 token。下一次送入的是刚选出的回答 token。如果把提示词最后一个 token 再送一次，就重复消费了输入，后续状态也会错位。

模型和运行程序各负责什么

OM 计算 embedding、网络层和 logits；宿主运行程序负责整理输入、维护状态、选择 token、检测结束标记，并把 token 还原为文字。一个 OM 文件需要与理解它接口的运行程序配套使用。后文中不同模型的输入输出数量差异，就是为什么旧运行程序常常不能直接用于新模型。

04 / 历史信息怎样保留

注意力、KV 缓存和 context 的联系

注意力：当前内容应该参考哪些历史内容

在标准自注意力中，输入会被投影成 Query、Key、Value，常写成 Q、K、V。你可以把 Q 看作“当前要寻找什么”，K 看作“各位置提供什么检索线索”，V 看作“检索后取出的内容”。这是帮助理解用途的类比；实际运行的仍是向量和矩阵运算。

模型计算当前 Q 与各个历史 K 的匹配分数，经过缩放和 softmax，形成一组权重，再对相应 V 加权求和。不同注意力头可以使用不同的投影，学习不同的信息关系。

进一步看：标准注意力的常见公式
Attention(Q, K, V) = softmax(QKᵀ / √d + M) V

d 是每个头的相关维度，M 是遮罩带来的偏置。允许访问的位置通常加 0，不允许访问的位置加一个能使其 softmax 权重为 0 的极小值。不同架构还可能增加归一化、门控等操作，导出器需要遵守对应模型的实现。

KV 缓存：复用已经算过的历史信息

生成下一步时，历史 token 的 K 和 V 可以保留下来，避免再次执行它们的投影等计算。新 token 只增加自己的 K、V，并用自己的 Q 访问历史缓存。

本项目常见的单个 K 或 V 张量形状是：

[batch 数, KV 头数, 缓存长度, 每个头的维度]

例如 Qwen3 0.6B 的单层、单份 K 缓存，context 1024 时是 [1, 8, 1024, 128]。这里的数字要从配置中读取：Qwen3 这份配置的 head_dim=128，不能简单用隐藏维度 1024 除以 Query 头数 16，擅自推成 64。

GQA 为什么能节省缓存

GQA 是 Grouped-Query Attention，即分组查询注意力。它允许多个 Query 头共享一组 K/V 头。例如本地 TinyLlama 有 32 个 Query 头、4 个 KV 头；Qwen3 有 16 个 Query 头、8 个 KV 头。缓存通常按 KV 头数存储，因此不能只根据 Query 头数估算缓存大小。

固定缓存：把“不断变长”改为“在固定位置写入”

原生框架可以通过动态缓存对象追加历史。为了构造静态图，本项目提前分配长度为 L 的张量，每一步只更新其中一个位置：

# 教学伪代码：位置 p 由输入张量给出
updated_K = Where(slot_index == p, current_K, previous_K)
updated_V = Where(slot_index == p, current_V, previous_V)

# 读取时只能访问位置 0 到 p
allowed = (slot_index <= p)

Where 在这里相当于对每个位置做一次选择。它把“更新哪一格”写成张量运算，便于 ONNX 记录。未写入的位置虽然已经占有张量空间，但会被注意力遮罩挡住，不应被当作真实历史读取。

读到这里，你应该能区分：权重保存模型学习到的参数；缓存保存这一次输入和生成过程中产生的状态。换一次独立对话，状态需要按运行协议重新初始化；训练权重仍然是同一份。
05 / 容量与形状

“模型支持多长”其实有三层含义

层次它回答什么为什么需要区分
原生模型的位置与长度设计模型配置、训练方案和官方评测允许怎样的序列。配置能索引某个位置，不自动证明该长度下的实际任务质量。
本次导出 / 编译容量这个 ONNX / OM 的缓存和接口能容纳多少序列槽位。本项目的 context 728、1024、2048 等在这里确定。
当前任务剩余预算扣除模板、历史、文字和图片后，还能生成多少。同一份 OM，输入不同，剩余容量也不同。

本项目采用保守的总容量契约：输入与计划生成的 token 共同受 context 限制。它不是“输入能放 1024，再额外回答 1024”。后文会把图片也加入这个预算。

为什么改变 context 通常要重新导出

在这批固定图里，长度 L 直接进入 KV 张量形状、写入遮罩和读取遮罩。1024 版本的接口接收的是长度 1024 的缓存。要换成 2048，需要产生具有相应形状和常量的 ONNX，并重新经过数值验证、ATC 编译。

这个过程主要改变推理容量和图的形状，沿用原始训练权重。它与“为了真正超出原生能力而扩展模型长文质量”是不同的问题。后者还涉及位置编码方案、训练或适配方法、长文任务评测与资源预算。

例如本地 TinyLlama 的 max_position_embeddings=2048，这次制作 context 1280，处于原配置范围内。Gemma3 的局部窗口 512 则是某些注意力层的读取范围，并不等于整个模型只能容纳 512。

进一步看：静态形状是不是唯一方案

不是。工具链可能支持某些动态形状或多个形状档位，推理框架也可以采用不同的缓存管理方式。但要逐算子、逐版本确认支持，并重新设计和验证接口。本项目选择固定 batch、固定缓存容量、单 token 步进，是这次实际验证的路线；不能把它描述成所有 NPU 部署的唯一方式。

长度变化，不等于权重按比例变大

同一模型从 context 1024 改成 2048，主要是长度相关的缓存、图常量和计算预算变化。模型的大部分训练权重仍相同。因此不能把 context 翻倍直接理解为模型参数量或 OM 文件大小翻倍。

06 / 从原模型到 OM

实际转换流程，一步一步做什么

图 1：先确认数值链路，再进行目标编译。每个箭头都表示一个需要明确输入输出的交接。

第一步：锁定输入模型和目标

先读取元数据，核对架构与张量形状，确认权重分片完整。再确定 batch、总上下文、是否保留图片、图片规格、目标 SoC 和精度方案。文件哈希用来识别同名文件是否实际相同；它证明内容身份，不评价模型质量。

本地文件夹后缀 A、B 只是项目标签，不能自动当成官方产品分支。本次成功的 2B 图文包来自 2b Qwen3.5A。其上游 revision 未完全确定，因此构建记录以本地文件内容和 SHA256 固定输入版本。

第二步：建立可导出的适配层

原生模型可能依赖 Python 缓存对象、条件分支、原地更新、动态列表，以及特定 GPU 的融合内核。导出器需要把本次推理所需的路径，明确表达为可以被计算图记录的运算。

这次 Qwen3 基于固定提交的现有导出器适配；Gemma3 和 TinyLlama 使用对应原生网络层加固定缓存封装；Qwen3.5 增加显式循环状态、固定 KV 与图文桥接。它们共享工作方法，但不是同一份代码换一个文件夹就通用。

第三步：用独立原生进程生成参考

参考程序加载原生模型，用 FP32 执行预定样例，保存 logits 和状态。导出适配器则在另一条路径运行。特别是存在 monkey-patch 时，进程隔离可以防止“参考实现也被同一段补丁改过”，避免两边犯相同错误而互相证明正确。

第四步：导出 ONNX 并检查完整性

ONNX 把推理过程表示成图：节点是运算，边是张量。shape 表示数组各个维度有多大，dtype 表示每个元素用什么类型保存。两者都是模型接口的一部分。

导出器需要给输入输出命名，明确 token ID、位置、缓存、视觉特征等张量的含义。项目主要采用 opset 15：opset 可以理解为 ONNX 运算规范的版本集合。它要与导出器、ONNX Runtime 和 ATC 的实际支持范围共同匹配。

第五步：通过数值门槛，才进入编译

先做小规模结构自检，再检查全量图与原生参考是否足够接近。关键检查包括多步生成、缓存保留、边界位置以及多模态子图串联。下一章会具体解释这些指标。

第六步：编译与交付

CANN 是昇腾的软件工具链，ATC 是其中进行离线模型转换 / 编译的工具。它根据真实图的输入、目标芯片和精度策略生成 OM。成功需要同时看到命令正常退出、最终成功日志，以及本次新产生的非空 OM 文件。

完整交付还包含 tokenizer、预处理、接口、验证报告、ATC 日志和哈希清单。只有 OM 文件而没有这些配套信息，后续开发运行程序时会缺少关键依据。

编译机与开发板的分工

宿主 CPU 负责加载模型、生成参考和运行 ONNX 验证；容器提供一致的 CANN 编译环境；目标开发板上的 NPU 负责最终执行 OM。离线编译可以在没有目标 NPU 的机器上进行，但最终的加载、精度、内存和速度仍应由目标设备验证。

07 / 计算图与目标编译

ONNX 是中间表达，OM 是目标运行模型

为什么要经过中间计算图

PyTorch 表达模型的方式很灵活，硬件运行时需要更明确的运算关系。ONNX 就是一种交换用的图表示：例如“先矩阵乘，再加偏置，再做归一化”，可以从框架代码转成一个带类型和形状的图。

OM 则由工具链按目标平台生成，包含用于目标运行时的模型信息、参数和执行安排。它与 NPU 型号、工具链版本、算子支持和输入接口有关，不能当作跨全部芯片和全部运行时的通用二进制文件。

大模型为什么会有外部权重文件

较大的张量直接装进一个 protobuf 消息，会遇到大小限制和内存开销。因此 Gemma3、TinyLlama 和 Qwen3.5 的部分导出流程先生成不带权重载荷的图，再把参数绑定为外部 initializer。图内记录外部文件名、偏移和长度。

onnx/
  model.onnx           # 运算与外部数据位置

08 / 数值验证

能导出、能编译，与算得正确是不同检查

转换中的很多错误不会让程序立刻崩溃。位置偏移一格、图像顺序错误、缓存更新覆盖旧位置，都可能产生正常形状的张量和看似通顺的回答。验证需要观察内部数值与状态，而不只是看模型有没有输出一句话。

第一层：结构和有限值

ONNX checker 检查图是否符合规范；接口核对检查名字、shape、dtype；有限值检查确认没有出现 NaN、无穷等异常。它们能排除一批基础问题，但不等于计算已经与原模型一致。

第二层：比较 logits 与中间状态

最大绝对误差看差得最远的那个元素；RMSE看整体误差规模；余弦相似度看向量方向是否接近。三者观察角度不同，不能互相简单替代。

进一步看：RMSE 怎样计算
RMSE = √[ ((a₁−b₁)² + … + (aₙ−bₙ)²) / n ]

它把每个元素的差平方，求平均，再开方。RMSE 与被比较数值使用相同的单位。它不是“准确率”，也不能直接乘 100 变成模型能力损失百分比。余弦相似度接近 1 也仍可能存在某些元素误差，所以项目同时检查不同指标。

对缓存，还会使用绝对误差与相对误差结合的预算。例如按 atol + rtol × |参考值| 建立允许范围。循环状态和其他缓存可以使用不同门槛，因为它们的数据分布与数值敏感性不同。

第三层：连续生成，而不只测试第一步

如果每步都产生一点误差，后续状态可能继续受影响。项目不仅比较单步输出，还从空状态连续处理短文本或图文提示，检查各步状态，并验证 8 个贪心生成 token 是否与参考一致。

数值验证常使用相同输入来隔离计算差异；随机采样会把采样噪声混进对比。因此项目用贪心 token 一致性辅助判断，但仍保留 logits 与状态门槛。生成的文字相同，不代表内部状态误差一定合格。

第四层：真实前缀与高位置边界

只用全零缓存测第 2047 个位置，不能代表模型实际读过前面 2047 个 token。项目用原生模型处理真实前缀，取得当时的合法状态，再在选定高位置比较 ONNX 步进。

长前缀参考可以按 64 个 token 分块执行，减少某些参考计算的峰值开销。这是参考程序的处理方式，不表示本次 OM 已有一个 64-token 并行 prefill 接口。

Qwen3.5 的循环状态尤其需要真实前缀

KV 历史里还保留了不同位置的数组；循环记忆 S 是逐步更新后的压缩状态。你不能把一个较晚时刻的 S “截短”来当成较早状态。不同边界必须有与那个前缀对应的状态种子。

第五层：多模态的子图与串联

视觉特征本身要对比，decoder 自身要对比，两者连接后还要对比。项目使用原生完整图文 forward 与原生拆分执行检查交接，再使用实际 ONNX 视觉输出驱动 ONNX decoder，核对整条链路。

诊断时可以临时给 decoder 喂原生视觉特征，以判断误差更可能来自哪里；这类隔离诊断只证明被隔离的部分，不足以代替完整图文链路的通过结果。

数值一致性与识别质量要分别评测

一张合成图可以用来比较两个实现是否计算接近，但不能代表相机噪声、复杂场景、屏幕小字和整页文档的识别质量。转换验证主要回答“是否保留了原模型在这些输入上的计算行为”；任务评测回答“对真实用户任务是否足够好”。

10 / Qwen3.5 语言部分

它为什么不能只用旧的 KV 运行程序

Qwen3.5A 2B 的语言骨干重复 6 组结构：每组先有 3 层 Gated DeltaNet，再有 1 层全注意力，合计 18 层与 6 层。这份 2B 的前馈网络是稠密路径，不能把家族介绍中的所有 MoE 特性都套用到它身上。[Q]

DeltaNet 的直观含义：持续更新一张记忆表

全注意力保留各历史位置的 K/V。DeltaNet 在逐步推理中维护固定大小的循环记忆矩阵 S，用新的输入更新它，再从更新后的记忆中读取结果。它还使用短卷积状态 C，参与近期投影信息的处理。

理解状态的类比

KV 像按顺序保存的历史索引与内容；S 更像随着阅读不断改写的一张摘要表。摘要表尺寸可以固定，但它的数值取决于前面实际读过什么。这个类比用于理解存储方式，不表示 S 是人工语言摘要，也不表示模型可以恢复全部原始细节。

导出器的单 token 步进要明确完成：Q/K/V 投影、短卷积更新、Q/K 归一化、门控与衰减、循环记忆更新、读取、输出投影。原模型的训练参数仍然保留，适配层改变的是怎样把这一步表达成图。

这次显式维护的状态

状态数量每组形状精度与用途
S 循环记忆18[1,16,128,128]FP32，DeltaNet 的持续记忆。
C 短卷积18[1,6144,4]FP16，短卷积所需的投影历史。
K6[1,2,L,256]FP16，全注意力的 Key。
V6[1,2,L,256]FP16，全注意力的 Value。

L 是本次 decoder 的 context。S 与 C 的张量尺寸在这两个规格中不随 L 增长，K/V 的长度维度会随 L 增长。这是它与 28 层全注意力的 Qwen3 在缓存比例上的重要差异。

为什么 decoder 有 53 个输入、49 个输出

输入包含 5 个当前步参数：input_ids、position、rope_position、image_embed、is_image。再加上 18 S、18 C、6 K、6 V，共 48 组状态，总共 53 个输入。输出为 logits 加更新后的 48 组状态，总共 49 个输出。

旧 Qwen3 运行程序通常只认识 token、position 和 K/V。把这份 Qwen3.5 OM 交给旧程序，即使文件能够找到，仍会缺少模态标记、三轴位置与循环状态管理。调用协议需要按实际接口重写或适配。

进一步看：循环状态为什么保留 FP32

循环记忆参与连续的乘法、衰减和增量更新。持续把结果存回较低精度，可能让舍入影响后续步骤。项目按本次验证结果把 S 保持为 FP32，同时让语言权重和其他部分状态使用 FP16。这是具体精度方案，不是声称所有模型或所有循环网络都必须采用完全相同设置。

11 / Qwen3.5 视觉详解

一张照片，怎样进入语言模型

Qwen3.5 的视觉编码器先把图片变成有顺序的特征向量。语言 decoder 再把这些向量与文字一起处理，生成文字回答。视觉输出与语言输入之间的对齐关系已经包含在原有训练权重中。

图 2：视觉 OM 处理一次图片，decoder 按序处理图像特征和文字。运行程序负责把状态与下一步输入接起来。

第一步：把原图变成固定规格

本项目的预处理先根据 EXIF 修正方向，转为 RGB，然后保持宽高比缩放，使用 BICUBIC 重采样，居中放到灰色画布上，补齐为 640×640 或 768×768。

例如 4000×3000 的照片缩到 768 规格时，内容约为 768×576，上下各补 96 像素；缩到 640 规格时，内容约为 640×480，上下各补 80 像素。这样保留原始长宽比例，避免把人物或物体横向拉伸。

接着把 0～255 的像素值转成 FP32，按 (像素 / 255 − 0.5) / 0.5 归一化，大致落到 −1～1。数值范围、颜色通道和排列顺序都是输入契约的一部分。

这套固定预处理的来源与边界

本地 A 检查点缺少原始图像 processor 配置。项目参照官方配置和实现，提供了固定尺寸的缩放补边与 patch 排列，并验证了同一输入下的原生与 ONNX 计算。它不是对官方所有动态分辨率策略、原图裁剪策略或真实照片效果的完整复现声明。

第二步：切成 16×16 的 patch

模型的 patch_size 是 16，意味着每个空间 patch 起源于 16×16 的像素区域。颜色有 3 个通道，时间 patch_size 为 2。对于静态图片，程序复制同一帧，使它满足这个时空输入布局。

每个展平 patch 的数值个数 = 16 × 16 × 3 × 2 = 1536

两个重复帧组成一个时间 patch，因此本次 image_grid_thw 的时间网格为 1。它不会因为重复一帧就让最终的视觉 token 数再翻一倍。当前输入协议只实现单张静态图片，不能据此当作视频推理接口。

第三步：视觉网络把 patch 变成特征

本地 2B 模型的视觉编码器有 24 层，内部隐藏维度为 1024。它用原有训练权重，把像素 patch 投影成特征，并通过注意力等计算融合图像信息。网络中的位置编码帮助区分不同空间位置。

配置里的 num_position_embeddings=2304 属于视觉位置表，不能把它理解成 decoder 的 context，也不能简单说成所有输入图像的统一容量上限。导出器针对本次固定网格，调用已有位置插值和旋转位置计算，提前保存相应常量。

进一步看：为什么把 patch Conv3D 写成线性投影

原生 patch embedding 的卷积核覆盖一个时空 patch，步长也是对应的 patch 大小，patch 之间不重叠。把每个 patch 按同样的顺序展平，再把卷积核按对应顺序展成矩阵，可以用一次线性投影表达同样的加权求和。项目保留原有卷积核与偏置，改变图中的表达方式；正确的展平顺序和张量形状是等价的前提。

第四步：2×2 合并，投影到语言维度

模型的 spatial_merge_size=2。原模型已经训练好的 merger 把相邻 2×2 空间 patch 特征分组，并经过它的归一化、线性层和激活等运算，输出语言主干需要的 2048 维向量。它不是简单地把四个像素块取平均。

640：40×40 个 patch → 20×20 = 400 个视觉 token
768：48×48 个 patch → 24×24 = 576 个视觉 token

每个位置最初对应目标画布上一块 32×32 的区域，但经过视觉注意力后，向量已经能融合其他位置的信息。不要把它理解为只保存那个小方块的原始像素。

看看图片怎样占据固定视觉网格

成功版本视觉图输出 [400,2048] 或 [576,2048] 的 FP16 特征。2048 与这份语言主干的 hidden_size 一致，所以它们可以在图像位置替代普通文字 embedding。

merger 与投影已经包含在 vision OM 内，当前交付是视觉 OM + 语言 OM两部分，不需要再找一份独立训练的投影器。更换为完全不同模型的视觉塔时，不能只凭向量长度相同就认定语义对齐。

项目的输入契约会生成这些坐标，并与原生模型的 get_rope_index 结果核对。回答阶段的三轴文本坐标从提示词 MRoPE 最大坐标加 1 继续；缓存槽位按实际提示词总长度继续。

一次完整图文调用，宿主程序的顺序

  1. 准备文字 token、400/576 个图像占位、三轴位置，以及固定形状的像素 patch。
  2. 调用一次视觉 OM，得到全部图像向量。
  3. 初始化 decoder 的 S、C、K、V 状态，按提示词顺序逐步调用 decoder。
  4. 文字位置传 token；图像位置传对应特征与图像标记；每一步回传更新后的全部状态。
  5. 用最后一个提示词位置的 logits 选择第一个回答 token。
  6. 把新回答 token 逐步送入 decoder，并更新两套位置，直到结束标记或总容量边界。

当前接口没有专门的多 token 并行图像 prefill 图，因此 400/576 个视觉位置也逐步处理。图片内容被纳入提示词状态后，同一段连续生成不需要每生成一个字就重新运行视觉编码器。

进一步看：不发图片时如何使用

可以走纯文本输入路径：不运行视觉图，不插入图像占位，decoder 使用文字 embedding 和相应位置。运行程序仍要符合这个 decoder 的混合状态接口，不能因此退回旧 Qwen3 的 KV 协议。已经生成的静态图仍然按照编译容量分配其要求的状态。

13 / 一次实际的数值问题

视觉部分为什么没有一路使用 FP16

精度方案不是根据文件大小猜出来的。早期全图文验证中，短文本与一些高位置测试可以通过，图片路径的部分 logits 和卷积状态却超过了原定门槛。更值得注意的是：当时生成的 8 个贪心 token 可以一致，但内部状态检查仍然不合格。

先隔离 decoder 与视觉来源诊断时使用独立原生视觉特征喂入 decoder，帮助区分是语言状态逻辑有问题，还是视觉特征误差进入后续计算。
提高视觉内部计算精度把视觉权重与内部运算保持为 FP32，输出继续采用 FP16 图像向量。某些图文状态检查仍受输入舍入影响。
同时保留 FP32 像素输入避免像素在进入 FP32 视觉运算之前先转成 FP16。然后用实际 ONNX 视觉输出，重新执行完整图文门槛。
保留混合精度进行编译完整数值验证通过后，使用 must_keep_origin_dtype 编译视觉与 decoder，保持图内各部分 dtype。

成功方案具体是怎样的

部分成功构建中的精度这样安排的目的
视觉像素输入FP32避免视觉计算前先发生一次 FP16 舍入。
视觉权重与内部运算FP32控制视觉路径中的计算误差。
视觉输出FP16保持与语言侧的特征桥接接口一致。
语言主干权重FP16沿用本次语言图的主要权重安排。
S 循环记忆FP32保留循环更新所需的数值精度。
C、K、V 状态FP16采用已通过验证的状态格式。

FP16 权重转成 FP32 后，不会恢复权重最初没有保存的细节。这里得到的收益是后续计算采用更高精度，减少运算中的舍入和累积影响。它不是重新训练，也不意味着模型因此学到了新知识。

修正之后继续使用既定门槛重新验证。图文链路的最终通过结果来自真正的 ONNX 视觉图加 ONNX decoder，而不是只用原生视觉特征完成的隔离诊断。

更高精度也有资源代价

本地视觉模块共有 331,416,576 个存储参数元素。纯参数数据由每个 2 字节改成 4 字节，增加约 0.617 GiB；视觉中间张量也可能增大。真实 NPU 的峰值内存与速度还受编译布局、缓冲与算子实现影响，不能只用这一个数字推断。

图片尺寸与 decoder context 是两根独立的轴

vision 决定图片处理形状与输出向量个数；decoder context 决定序列状态容量。对本项目的单向量步进 decoder 而言，图片特征数量由宿主输入序列体现，而不是“decoder 一次必须接收 400 个向量”的固定大输入。

因此，在相同检查点、2048 维桥接、dtype、token 标记与位置协议都匹配的前提下，更改视觉尺寸不要求重新训练 decoder。但要有完整的预处理、容量检查、位置生成与串联验证。本文已经证明的组合只有表中的两组，其他交叉组合属于待验证组合。

768 一定比 640 好吗

这不表示总耗时精确变成 2.07 倍，因为其他算子、编译实现、内存带宽与 decoder 开销并不按同一个比例变化。对于很长的截图或整页小字，单次缩到一个方形画布可能仍损失细节；分块、裁剪、多图或 OCR 等方案需要另外设计，当前单图接口没有自动提供这些能力。

15 / 资源预算

权重、缓存、激活与运行时要分开算

硬盘上的文件大小、宿主导出时使用的 RAM、NPU 推理时的内存，是三个不同量。编译中还可能同时存在原生模型、参考数组、图与外部权重，因此宿主峰值也不能用最终 OM 文件大小直接代替。

全注意力 KV 的基础公式

KV 字节数 = 2 × 层数 × batch × KV 头数 × context × head_dim × 每元素字节数

单份缓存远不是完整 NPU 内存

  • 权重：模型参数及编译布局后的常量。
  • 状态与输入输出：运行程序可能同时持有输入、输出或双缓冲。
  • 激活：网络层执行时产生的中间结果，视觉注意力的部分张量可能较大。
  • 工作空间：算子与运行时需要的临时区域。
  • 系统和其他进程：开发板的可用内存还受操作系统与其他程序影响。

按本地参数头部，Qwen3.5A 存储约 22.13 亿个参数元素，其中视觉约 3.31 亿。若语言参数按 FP16、视觉参数按 FP32，纯参数数值约为 4.74 GiB。这个估算没有包含编译后的额外布局、输入输出和激活，不能据此断言某块板子一定能装下。

8T 与 8GB 不是同一个量

开发板标识中的 8T / 8 TOPS 描述特定条件下的运算吞吐量，GB 描述存储容量。二者不能互相换算。宣传算力还受到精度与算子条件限制，也不能直接换成这个语言模型每秒生成多少 token。

为什么参数更少，缓存反而可能更大

权重规模与状态结构由不同因素决定。Qwen3 0.6B 有 28 层全注意力、8 个 KV 头；Qwen3.5A 2B 只有 6 层全注意力并使用 2 个 KV 头，其余层保存固定 S/C。因此后者在某些长度下的逻辑状态更小，却仍拥有更大的权重和额外视觉计算。

同样，更少的逻辑状态也不自动保证更快。循环更新的算子实现、内存传输、KV 整体输入输出的开销、融合程度，都要结合目标设备实际测量。

17 / 读者问答

把常见困惑一次讲清楚

转成 OM 后，模型会更聪明吗？

转换目标是保留已有模型在指定条件下的推理行为，并使它能在目标硬件运行。知识和能力主要来自原有训练。编译优化可以影响执行效率，数值精度安排可能带来差异，因此需要验证；它本身不提供新的训练知识。

有了 safetensors，为什么还不能直接生成一个通用 OM？

权重需要对应架构才能解释。不同模型有不同的层、位置编码、状态和预处理；ATC 还需要支持导出图里的算子。通用工作流可以统一检查与记录，但支持程度必须逐模型验证。

把 config 里的 max_position_embeddings 改大就能扩容吗？

那只是修改了一项配置声明。还需核对位置编码、导出缓存、编译图和长文质量。超出模型原先的设计或评测长度，可能需要额外适配或训练与专项验证。本项目 TinyLlama 1280 仍在其本地 2048 配置范围内。

改变 context，是改 ONNX 还是只改 OM？

在这批静态图中，context 进入 ONNX 的张量形状和常量，因此通常重新导出对应 ONNX、验证后再编译 OM。只有图本来就设计并验证了合适的动态形状 / 多档形状，才可能采用其他路线。

640 与 768 会改变原模型的 hidden_size 吗？

不会。视觉内部 hidden_size 仍为 1024，桥接输出仍为 2048。变化的是图片网格、位置相关常量和输出 token 个数。decoder context 也不会把 hidden_size 改成 1024 或 2048；两者只是这里恰好出现了相同数字。

图片大小 4MB，是不是比 2MB 多占一倍 context？

不是按压缩文件字节计算。在这套固定规格里，两张图只要都处理到 640×640，就都产生 400 个视觉 token。原图分辨率、压缩质量和缩放损失仍影响图像内容质量，但不按 MB 直接换算 token。

图片会变成一段文字，然后交给语言模型吗？

这条路径直接使用视觉向量，并在对应位置替代文字 embedding。图像识别与回答依赖整个图文模型的训练关系。若另外加入 OCR，把识别出的文字送入语言模型，那是另一条可以设计的应用路径。

同一图片问第二个问题，必须重新运行 vision 吗？

如果程序保留了适合复用的视觉特征，且预处理规格和模型保持一致，可以设计特征复用。但对话状态还必须正确组织：保留完整对话时按协议继续；重新建立提示词时重新喂入相应图像位置。当前交付的接口说明并不自动提供一个多轮缓存服务。

能把 vision_640 与 decoder_ctx2048 搭配吗？

从这份 decoder 的单向量接口看，尺寸和容量是两个轴；在同一检查点、特征维度与 dtype 相同、位置与模板规则正确、总容量足够时，可以设计这种组合。但它不属于本文已经通过完整串联验证的两组组合，需要补做预处理、数值与运行验证。

视觉独立了，换任何模型的 vision 都可以吗？

不可以只看向量维度。特征的语义空间、投影权重、标记、顺序与位置规则都要匹配。即使两个向量都长 2048，也不代表它们具有相同含义。来自同一套配套权重的拆分部署，与更换视觉编码器是不同工作。

为什么图片向量都已经送进去了，回答还会慢？

首个回答前要完成视觉计算、图文预填充，以及宿主与设备之间的调用和状态管理。当前图文 OM 每步处理一个位置，400/576 个图像位置本身就需要多次调用；生成时还有模型权重、算子与内存带宽开销。

FP32 视觉是否意味着整个模型都是 FP32？

不是。成功图内视觉输入与内部计算为 FP32，视觉输出为 FP16，语言主干主要使用 FP16，S 循环状态为 FP32，其他指定状态为 FP16。实际接口记录定义每个张量的类型。

把 FP16 权重变成 FP32，为何仍然可能更准？

原有权重数值不会凭空获得更多来源精度，但计算时的中间结果可以用 FP32 表达，从而减少运算舍入。它改变计算误差路径，不恢复已经丢失的权重细节，也不自动增加模型能力。

缓存小的模型，是否一定更省内存、更快？

缓存只是总开销的一部分。权重、视觉激活、输入输出副本、工作空间和运行时也要计算；不同结构的算子支持和融合情况会影响速度。最终需要在目标设备用相同条件测量。

同样的回答，为什么状态检查仍可能失败？

只要最高分 token 没变，贪心输出就可能相同，但其他分数与状态已经发生超限偏差。继续更长输入时影响可能扩大。因此项目同时核对 token、logits 与状态，不用短期输出一致替代内部验证。

为什么本地数值通过，还要再测开发板？

ONNX Runtime CPU 执行的是导出图；NPU 执行的是 ATC 编译后的模型和目标算子。它们还涉及目标精度实现、运行时接口、缓冲、内存和驱动兼容性。板端验证补上的是这一层证据。

词表更大、参数更多，是否可以直接排能力名次？

不能。训练数据、训练方法、任务类型、指令适配、tokenizer、上下文和推理设置都会影响结果。本文比较的是结构与转换处理，项目没有用同一套任务评测给这些本地检查点建立能力排行榜。

18 / 术语速查

读到陌生词时，从这里找回含义

参数 / 权重
训练学习并保存的矩阵、向量等数值。
检查点 Checkpoint
某个具体模型版本保存下来的权重与配套信息。
张量 Tensor
有维度、形状和元素类型的数组；向量和矩阵都是例子。
shape
数组每个维度的大小，例如 [1,2,1024,256]。
dtype
数组元素的编码类型，如 FP16、FP32、INT64。
batch
一次同时处理多少组样本；这批图主要固定为 1。
token / token ID
模型处理序列的单位，以及它在词表中的整数编号。
tokenizer
按模型规则把文字与 token ID 互相转换的组件。
聊天模板
把角色、消息和生成提示组织为模型期望格式的规则。
embedding
把离散 token ID 映射到连续数值向量的表示。
hidden_size
网络某类隐藏表示的向量长度，与 context 是不同维度。
logits
下一步词表候选的原始分数，不是最终文字。
自回归生成
根据已有序列预测下一步，再把新结果接回去继续预测。
贪心选择 Greedy
每步取分数最高的候选 token。
Prefill
处理输入提示词并建立状态的阶段。
Decode
在已有状态上逐步生成新 token 的阶段。
Q / K / V
注意力中的 Query、Key、Value 三类投影。
KV Cache
为了复用历史注意力计算而保存的 K、V 状态。
GQA
多个 Query 头共享较少 K/V 头的注意力组织方式。
因果遮罩 Mask
限制当前位置只能读取允许的历史位置。
滑动窗口
让某些层只关注一定范围内的近期位置。
RoPE
通过旋转方式把位置信息引入注意力表示。
MRoPE
把图像等内容的多轴位置组织进旋转位置编码。
Gated DeltaNet
本项目 Qwen3.5 中使用循环记忆与门控更新的一类网络层。
S / C 状态
本项目的循环记忆矩阵 / 短卷积历史状态。
patch
图片按规则划分并排列出的像素块输入。
merger
原模型训练好的视觉特征分组、合并与投影模块。
视觉 token
进入图文序列的图像特征位置，不是 tokenizer 识别出的普通文字。
ONNX / opset
计算图交换格式 / 对应运算规范的版本集合。
外部数据 External Data
计算图引用的独立张量数据文件。
CANN / ATC
昇腾软件工具链 / 其中的离线模型转换与编译工具。
OM / AscendCL
昇腾运行模型文件 / 用于开发模型加载、内存与执行等应用的接口体系。
RMSE
均方根误差，衡量一组数值的整体差异规模。
SHA256
内容摘要，用来识别与核对文件内容身份。
MiB / GiB
二进制容量单位：1 MiB=2²⁰ 字节，1 GiB=2³⁰ 字节。
TOPS
每秒万亿次运算的吞吐量单位，需结合精度和计算条件理解。
